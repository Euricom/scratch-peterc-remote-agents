Remote agent access

Keep your coding agents running, and reach them from anywhere

1 network layer 4 setups Peter Cosemans · Euricom
Welcome. Today: how to keep Claude Code working while you are away from your desk, and four concrete setups to reach it, starting with the network layer that makes the self-hosted ones possible. Press S for this window, ? for the keys.

Agents work for hours but need you for seconds

They run for hours

A long refactor shouldn't stop when you close the laptop.

They need you briefly

A permission prompt or a question. Answer it from your phone.

Many in parallel

Several sessions at once. You supervise, they work.

Running example: you work on your laptop, Claude is halfway through an api-refactor. It's 17:30: close the lid, drive home. The agent has to keep running on the dev server at home or the office.

The shift: from pairing with an agent at your desk to supervising agents that keep running. You check in, unblock, review, from wherever you are. Introduce the running example and come back to it on every option: you do your main work on the laptop. Claude Code is mid-refactor, you want to pack the laptop and drive home, and continue from the couch (laptop again, or phone). Closing the lid is sleep: an agent running ON the laptop stops. So every option answers one question: where does the session live while the laptop is in the car? The answer for 01 to 03: on the dev server at home or at the office that stays on. The laptop (and phone) only connect to it. The scenario is illustrative.

What we want: a private network that follows us around, with nothing exposed.

Every self-hosted option that follows depends on this. Your machine sits behind a home router or corporate NAT. Opening ports to the internet is the classic answer, and the wrong one. Exception to mention now: the Claude-hosted option (04) runs in Anthropic's cloud, so it doesn't need this.

$ curl -fsSL https://tailscale.com/install.sh | sh $ sudo tailscale up $ ssh me@dev-server # from anywhere
  • No open ports. NAT traversal, nothing exposed
  • MagicDNS. Machines by name: dev-server, winpc

Tailscale builds a WireGuard mesh, your "tailnet". Every device gets a stable private IP (100.x) and a name. Install, log in with SSO, done. Free for personal use. Tailscale Serve matters later: t3code uses it to publish its local port 3773 as https://dev-server.<tailnet>.ts.net, tailnet only. A stable IP also changes the mosh story (option 01, herdr + mosh). Tailscale SSH is off by default and tempting to turn on. Don't: in check mode it waits for a browser login that Cursor and VS Code remote sessions never show, so they hang. Plain sshd over the tailnet works for everything. Already on? "sudo tailscale set --ssh=false" on the server (drops its sessions). ServerAliveInterval 30 in ~/.ssh/config keeps idle sessions alive.

$ mosh me@dev-server -- herdr # SSH logs in, mosh carries it, herdr keeps the agents
Source: mosh.org. The mosh client logs in via SSH (same keys, same config), starts mosh-server and switches to UDP. Datagrams are encrypted and authenticated with AES-128 in OCB3 mode. It handles packet loss and adapts the frame rate to the network; it doesn't fill network buffers, so Ctrl-C always halts a runaway process. No root needed. Limits: it syncs only the visible screen, so use tmux for scrollback and to reattach after closing the client. Over Tailscale the UDP ports need nothing on the router. herdr (github.com/ogulcancelik/herdr) runs on the server: panes survive the client going away, "herdr" reattaches, and each pane is marked working, blocked or idle. mosh + tmux would also tick "reattach", but not "which agent needs you". Pure SSH ticks "switch network" only thanks to Tailscale's stable IP. Full comparison as a live demo after option 01.

herdr is the tool that holds it all together: every Claude Code session runs in its own herdr pane on the server, herdr shows which one is working, blocked or idle, and it keeps them running when you disconnect. Three parts: a terminal on the laptop (or phone), the tailnet in the middle, and the server where every Claude Code session runs inside herdr. SSH alone works; mosh is the optional upgrade. Install herdr with "curl -fsSL https://herdr.dev/install.sh | sh", then "herdr integration install claude" for richer Claude status. Think tmux, but agent-aware. Source: github.com/ogulcancelik/herdr (Apache 2.0, Rust). Install also via brew install herdr. ctrl+b q detaches, running herdr again reattaches. Two ways to attach (source: herdr.dev/docs/connecting-machines): "herdr --remote dev-server" runs the herdr client on the laptop and talks to the herdr server on dev-server over SSH. It retries by itself after a network drop, sleep or SSH failure (backoff up to 2 min), shows the last state dimmed meanwhile, and can keep several machines in one combined agent list. mosh can't help here: it only carries an interactive terminal, and herdr's remote link is SSH only. "mosh dev-server -- herdr" runs herdr on the server inside a mosh session: you get mosh's local echo on laggy links, but one machine per window. `herdr integration install claude` gives richer status for Claude Code (from the bitdoze write-up). Mobile: the bitdoze article says the Moshi iOS terminal has native herdr support; I haven't verified that myself. The status panel is illustrative, not a capture. mosh (mosh.org) replaces SSH for the interactive session: UDP, roams between networks, local echo. It syncs only the visible screen, so herdr (or tmux) provides scrollback and reattach. Needs UDP 60000-61000 and mosh-server on the server's PATH; over Tailscale nothing is opened on the router. Honest note: Tailscale already gives SSH a stable IP, so what mosh adds is surviving sleep and long outages, plus local echo. No herdr? "mosh dev-server -- tmux new -A -s main" then "claude" works too, you just lose the per-agent status. Phone clients: Blink Shell (iOS), Termux (Android). Running example: you close the lid at the office, open it at home, reattach, and api-refactor is the one marked blocked. Press down for the survival demo. [Add the herdr config used in the demo.]

Server mode flags worth knowing
--spawn worktreeA git worktree per session, no edit conflicts

* Desktop only uses /remote-control. For server mode run claude remote-control in a terminal (Desktop's Terminal pane works); it stops when that terminal closes.

"Always on" is "remoteControlAtStartup": true in ~/.claude/settings.json. A checked-in project .claude/settings.json can only turn it OFF, so a repository can't switch it on for everyone. Outside server mode, each process or Desktop session gets one remote session. In server mode, press spacebar to show a QR code for your phone. More server flags: --name "My Project" (title in the session list), --spawn same-dir (default, sessions share the folder) | worktree | session (exactly one), w toggles spawn mode at runtime; --session-id to resume a specific one; --[no-]create-session-in-dir (on by default); --chrome / --no-chrome lets remote sessions use Chrome on the host; --verbose, --debug-file for troubleshooting. Running example: halfway through api-refactor at 17:30, type /rc and the session follows you to the phone. Client vs host (if asked): closing the client (phone app, browser, Desktop on another computer) is harmless: the session keeps running on the host, push still reaches you, and you pick it up again with progress synced. Closing the host is what matters: lid closed, sleep or network drop: the session goes offline, work pauses, and it reconnects automatically on wake. terminal closed, Desktop quit, claude stopped: the session stops. Bring it back with claude --continue or --resume; server mode: claude remote-control --continue, within about 4 hours. long network outage with the host awake: interactive sessions (--rc, /rc, Desktop) keep working locally and reconnect; server mode gives up after about 10 minutes and exits. Security and data: outbound HTTPS only, short-lived scoped credentials, the transcript is stored at Anthropic for sync. Optional Trusted Devices (biometric step-up every 18 hours). disableRemoteControl turns it off org- or machine-wide. Some commands are local-only (/plugin, /resume). Many work remotely with an argument (/model sonnet, /effort high, /compact). Source: code.claude.com/docs/en/remote-control, checked 2026-11-04.

First: the host needs an SSH server, and it's often off by default

Windows 10 / 11

Only the SSH client is installed. Add the server as an optional feature (PowerShell as admin):

> Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0 > Start-Service sshd > Set-Service sshd -StartupType Automatic

macOS

Off by default. System Settings → General → Sharing → Remote Login.

Linux

Desktop installs often lack it: sudo apt install openssh-server.

Same lens as Remote Control: the remote machine is the host, your laptop is the client. Question: does the host process survive when the client goes away? Reaching the dev-server from outside is Part 1 (Tailscale); a server-side session manager that survives the disconnect is option 01. Not repeated here. SSH server per OS: Windows 10 (1809+) and 11 ship the OpenSSH client, not the server. GUI route: Settings, System, Optional features, View features, add "OpenSSH Server". The install normally adds the inbound firewall rule for port 22 ("OpenSSH-Server-In-TCP"); check with Get-NetFirewallRule if you can't connect. The default shell over SSH is cmd.exe; admin accounts use C:\ProgramData\ssh\administrators_authorized_keys instead of ~/.ssh/authorized_keys. Desktop SSH supports Windows hosts only with limits, so a Linux or macOS host is the smoother choice. macOS CLI alternative: sudo systemsetup -setremotelogin on. Linux: sudo systemctl enable --now ssh (sshd on Fedora/Arch). Desktop SSH: Claude runs under a background helper Desktop installs on the remote (Desktop v2.31226.0+). The helper stops after 30 days without a connection, and on Linux KillUserProcesses=yes can end the processes. Add SSH connection takes Name, user@host or a ~/.ssh/config alias, port, key, worktree folder. Auto-reconnect needs a login without a prompt (SSH-agent key). Extras: permission modes, connectors, plugins and MCP all work. Skills come from the remote ~/.claude/skills. No Browser pane or preview servers: ssh -N -L 3000:localhost:3000 dev-server. You can't move an SSH session to the cloud. Remote host: Linux/macOS (Windows with limits), SFTP enabled, about 1 GB free. Plain ssh: claude is a child of your SSH shell, so the disconnect (SIGHUP) ends it. From the phone: both show up in the Claude app with Remote Control on; plain ssh only while the SSH connection is alive. Running example: api-refactor on the dev-server; close the lid at 17:30. Desktop SSH keeps going, plain ssh dies. Press down for what the Desktop app can do over SSH.

Takeaway: prefer a Linux or macOS host. Windows needs more setup (OpenSSH Server, shell and tools) and has fewer Desktop app features.

Windows host shell: cmd.exe, PowerShell 5.1 or Git Bash. Your dev tools (node, yarn, git, gh) must be installed and on the PATH in that shell. The docs warn Windows gets less testing than Linux: try your own work there first.

What you actually get in the Desktop app when the session runs on a remote host. Linux and macOS hosts are the smooth path; Windows hosts work with limits. Files pane: view-only for SSH (and cloud, WSL) sessions; ask Claude to edit. On a Windows host the docs list no extra limit, but in my own test (2026-11-05) the files pane didn't work reliably. That's first-hand, not documented. Terminal: available in SSH sessions, on the remote, in the session's folder; expect one extra SSH login per terminal tab. On Windows it doesn't open when the session folder is a Windows path. Browser pane: Claude doesn't get the pane's tools in an SSH session, so it can't open or auto-verify your app, and the Dev servers menu and preview servers aren't available. Desktop also leaves LocalForward and friends off, so forward ports yourself. Create PR: Claude pushes and runs gh pr create on the remote, so install and authenticate git and gh there (git push, gh auth status). Merge when ready is disabled: turn on auto-merge on GitHub instead. MCP on Windows: on some hosts, MCP servers from claude_desktop_config.json are called through Desktop, so they don't work while Desktop is disconnected (on every Windows host before Desktop v2.37337.0). Worktrees on Windows: Desktop ignores a custom worktree folder. Windows host requires Desktop v2.31226.0 or later and Microsoft's OpenSSH Server. The shell the SSH server starts is where Claude runs commands, so node, yarn, git and gh have to work in that shell, not only in your usual terminal. Other Windows-host limits, if asked: commands run unsandboxed; with cmd.exe or PowerShell you may need to connect to see earlier messages and can fork only at the first message; a task keeps running while disconnected only if the SSH server lets programs outlive the connection, and leftover processes and the helper don't stop on their own. Source: code.claude.com/docs/en/desktop (SSH sessions, Windows remote machines), checked 2026-11-05.

  2. Remote Control always on: /config → Enable Remote Control for all sessions.
  3. Start sessions that outlive SSH: a Desktop SSH environment, or a herdr session on the server (option 01).

Good

  • Push on “done” or “needs approval”
  • Close the lid or the app: work continues

Watch out

  • Plain ssh + claude dies on disconnect
The punchline of this stack. Tested first-hand: SSH sessions started on my Windows host at home showed up in the Claude phone app. The diagram reads left to right: you start the session from your laptop over SSH, it runs on the always-on host, and Remote Control puts it on your phone. Both ends are clients; the host never closes. That's why closing the lid or the app is harmless. Setup: step 2 is the Always-on setting from the switch-it-on slide, applied on the SSH host: "remoteControlAtStartup": true in the remote ~/.claude/settings.json, or in Desktop under Settings, Code, Connect new sessions to Remote Control. Remote Control needs a subscription login on the host, not an API key, Bedrock or gateway. Step 3 matters: plain ssh + claude also shows up on the phone, but dies when the SSH connection drops (SIGHUP). Desktop SSH runs Claude under a background helper; a server-side session manager is option 01. The Remote Control docs recommend this pattern themselves: tmux/screen on a remote machine. Each on its own, if asked: Remote Control alone = zero network setup and your full local env, but the laptop must stay awake. SSH alone = closing the laptop is fine and lots of CPU, but the remote needs its own dev env (credentials, registry tokens, the right Node) and port forwarding for dev servers. Remote Control: the transcript is relayed through Anthropic; ZDR/HIPAA orgs can't use it. Desktop SSH disables ForwardAgent. Power-user variant: claude remote-control --spawn worktree on the host, so you start new sessions from your phone, each in its own worktree. Running example: api-refactor keeps running on the dev-server; close the lid at 17:30, the push "needs approval" arrives in the car park. One-liner: "Remote Control gives you a remote. SSH gives you a home that never sleeps."
